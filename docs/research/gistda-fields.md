# GISTDA API — confirmed fields, params, and limits (2026-09-26)

สรุปนี้แทนการวางผล `$B probe gistda` ยาวๆ กลับมาให้ Poom อ่าน — ทำครั้งเดียว
ตรวจกับ key สาธารณะ (demo key) ที่ GISTDA เองฝังไว้ในหน้าตัวอย่าง
"ลองใช้งาน" ของ `opendata.gistda.or.th/dataset/flood-disaster-data` และ
`.../disasters-02` (อ่านสด, ไม่เคยเก็บ key ไว้ที่ไหน) — **ไม่ใช่ key ของ
Poom**. รวม ≤ 30 คำขอ ห่างกัน ≥ 2 วินาที ตามกติกาที่ Poom วางไว้

**สถานะ license: รอ Poom ยืนยัน** — ทุกอย่างในไฟล์นี้เป็นข้อมูล SHADOW เท่านั้น
(`gistda_flood.py`'s own SHADOW MODE section) ไม่ขึ้นจอจนกว่า Poom จะยืนยันเงื่อนไขการใช้

## 1. bbox/pv_idn/ap_idn/tb_idn — พิสูจน์ว่ากรองได้จริง

โจทย์เดิม (รายงาน VPS 2026-09-26): "probe gistda" ขอ bbox รอบกรุงเทพฯ แต่ได้
พิกัดใกล้อยุธยา — ดูเหมือน bbox ถูกเมิน **ผลตรวจจริง: bbox กรองได้ถูกต้อง**
กล่องเดิมของ probe.py (`99.70,13.06,101.30,14.46`) กว้างเกินไป (สูง ~155 กม.)
ครอบคลุมทั้งกรุงเทพฯ**และ**อยุธยา — ไม่ใช่ปัญหาฝั่งเซิร์ฟเวอร์ (แก้แล้วในโค้ด:
กล่องใหม่เล็กลง อยู่ในกรุงเทพฯ ล้วนๆ)

ตัวเลขพิสูจน์ (endpoint `flood/1day`, วันที่ 2026-09-26):

| การขอ | numberMatched | ผลลัพธ์ |
|---|---|---|
| bbox เล็กรอบเชียงราย (99.75,19.85,99.95,20.00), ไม่มี pv_idn | 0 | ไม่มีจุดน้ำท่วมในกล่องนี้ |
| bbox เดียวกันแต่ย้ายไปรอบอยุธยา (100.50,14.30,100.65,14.45) | 43 | พิกัดจริงอยู่ในกล่อง (lon 100.577-100.627, lat 14.298-14.327) |
| `pv_idn=57` (เชียงราย) อย่างเดียว ไม่มี bbox | 0 | ตรงกับผล bbox |
| `pv_idn=14` (อยุธยา) อย่างเดียว ไม่มี bbox | 3528 | มากกว่า bbox เพราะไม่ได้จำกัดพื้นที่ย่อย |
| bbox รอบอยุธยา + `pv_idn=14` พร้อมกัน | 43 | เท่ากับ bbox อย่างเดียว — ใช้ร่วมกันแบบ AND ได้ |

`pv_idn=14` คืนค่า `pv_tn: "จ.พระนครศรีอยุธยา"` ตรงกับรหัส "14" ใน
`kiosk_broker/data/provinces.json` พอดี — **pv_idn ใช้รหัสจังหวัด 2 หลักชุด
เดียวกับที่ broker ใช้อยู่แล้ว** ไม่ต้องสร้างตารางใหม่

## 2. limit/offset — ไม่มีเพดานต่ำอย่างที่คิด

`limit=5000` ในคำขอเดียว (endpoint `flood/1day`, `pv_idn=14`) คืนค่า
`numberReturned=3528` (ครบตามที่มีจริง, `numberMatched=3528` เท่ากัน) —
**ไม่มีเพดานเซิร์ฟเวอร์ต่ำกว่า 5000** อย่างน้อยก็ในคำขอนี้ ตัวเลข
`GISTDA_PAGE_LIMIT=200` ใน probe.py เป็นทางเลือกความสุภาพของ broker เอง
ไม่ใช่ข้อจำกัดของ GISTDA

## 3. sort — ไม่มีผล

`sort=asc` และ `sort=desc` บน `flood/1day` คืนลำดับ `_id` เหมือนกันทุกตัว —
ห้ามพึ่งพา `sort` ว่าจะเรียงตามที่ขอจริง

## 4. ไม่มีพารามิเตอร์เลือกฟิลด์/ข้าม geometry — และเป็นกับดัก

ลองแล้วไม่ได้ผลทั้งหมด: `properties=`, `select=`, `fields=`, `skipGeometry=true`,
`geometry=false` — ทุกตัวคืน **HTTP 200, `numberMatched: 0`** ไม่ใช่ error
และไม่ใช่ "เมิน" — **พารามิเตอร์ที่ไม่รู้จักถูกตีความเป็นตัวกรองเพิ่มที่ไม่มีทาง
ตรง จึงได้ 0 รายการเงียบๆ** ห้ามใส่พารามิเตอร์เดาในคำขอจริงเด็ดขาด (แก้ไว้
ในคอมเมนต์ของ `probe.py`/`gistda_flood.py` แล้ว)

## 5. ชื่อฟิลด์จริงใน `properties` (flood/1day..30days)

ยืนยันจากการเรียกจริง (ตัดข้อมูลภายใน GISTDA เอง เช่น `_id`/`_createdBy` ออก
เพราะเป็น id ภายในของ GISTDA ไม่ใช่ของ Poom):

```
pv_idn, pv_tn, ap_idn, ap_tn, tb_idn, tb_tn, lat, long,
file_name, flood_area,
_area, f_area, rice_area, cassava_area, maize_area, sugarcane_area,
building, hospital, school, population, length_road,
re_nesdb, re_royin,
_createdAt, _updatedAt, _createdBy, _updatedBy, _id
```

จุดสำคัญ (**ไม่มี** `img_date`/`date`/`area_km2`/`shape_area_km2` เลย — ที่
เดาไว้แต่แรกผิดทั้งคู่):

- **`file_name`** — รหัสภาพถ่ายดาวเทียมต้นทาง (คั่นด้วย comma ถ้ามาจากหลาย
  ภาพ) ฝัง `YYYYMMDD_HHMM` ไว้ในชื่อ เช่น `rd2_20260926_0613`,
  `S1C_20260921_0558`, `S1D_20260922_1819`, `cg2_20260919_1806` — **นี่คือ
  วันที่ความสด (freshness) ตัวจริง** พบ prefix หลายแบบ (rd2/S1C/S1D/cg2/cm4)
  = ดาวเทียม/เซนเซอร์คนละตัวที่ผสมกันในชั้นเดียว
- **`_createdAt`/`_updatedAt`** — เวลาที่ GISTDA เขียนลงฐานข้อมูลของตัวเอง
  ไม่ใช่วันที่ภาพถ่าย: ตรวจแล้วค่าเดียวกันหมดไม่ว่าจะขอ 1/3/7/30 วัน (คือเวลา
  รันงานประมวลผลของ GISTDA ไม่ใช่วันที่เหตุการณ์)
- **`flood_area`** — พื้นที่น้ำท่วมของทั้ง "ตำบล" (`tb_idn`) นั้น หน่วย **ไร่**
  (ยืนยันด้วยการตรวจสอบหน่วยไขว้ — ดูข้อ 7) **ค่าเดียวกันซ้ำในทุกแปลง
  (feature) ที่ตัดผ่านตำบลนั้น** — พิสูจน์แล้ว: ตำบลหนึ่งมี 33 แปลงต่างกัน
  แต่ `flood_area` เท่ากันทั้ง 33 แปลง — **ห้ามรวม (sum) ทีละ feature โดยตรง
  ต้องนับครั้งเดียวต่อ `tb_idn`** (แก้ไว้ใน `gistda_flood._fold_features`/
  `summarize_provinces` แล้ว)
- **`_area`/`f_area`/`rice_area`/ฯลฯ** — พื้นที่ **ต่อแปลง** หน่วยตารางเมตร
  (ไม่ใช่พื้นที่น้ำท่วม เป็นพื้นที่แปลงเกษตร/พืชแต่ละชนิด) อย่าเข้าใจผิดว่าเป็น
  พื้นที่น้ำท่วม

## 6. `flood-freq` (น้ำท่วมซ้ำซาก 2011-2024) — คนละ schema กันเลย

`flood-freq` เป็นข้อมูล**ต่อพิกเซล** (ไม่ใช่ต่อแปลงเกษตรแบบ flood/*day):

```
_collectionId, _createdAt, _createdBy, _id, _updatedAt, _updatedBy,
ap_code, ap_en, ap_idn, ap_tn,
area_rai, com_tn,
freq,
objectid,
pv_code, pv_en, pv_idn, pv_tn,
re_nesdb, re_royin,
shape_area, shape_length,
tb_code, tb_en, tb_idn, tb_tn,
y_2011, y_2012, ..., y_2024   (14 ปี — เกินชื่อ dataset "2011-2023")
```

- **`area_rai`** และ **`shape_area`** เป็นพิกเซล**เดียวกัน** สองหน่วย:
  ตัวอย่างจริง `area_rai=0.02199976850880807`, `shape_area=35.19962961360954`
  → `0.022 * 1600 ≈ 35.2` ✅ **ยืนยัน 1 ไร่ = 1,600 ตร.ม.** ใช้ตรวจสอบหน่วย
  ของ `flood_area` (flood/*day) ได้ด้วย เพราะทั้งสอง endpoint อยู่ใน dataset
  ตระกูลเดียวกัน
- **`freq`** — จำนวนปี (0-14) ที่ `y_2011..y_2024` เท่ากับ 1 นับตรงจากข้อมูล
  ไม่ต้องคำนวณเอง ตัวอย่าง: `freq=4` พร้อม `y_2011=1, y_2013=1, y_2017=1,
  y_2023=1` ตรงกัน — นี่คือ "จำนวนปีที่น้ำท่วม" ต่อพิกเซล
- ไม่มี `flood_area`/`img_date`/`date` เลยใน schema นี้ — ใช้ `_createdAt`
  แทนเป็น "ข้อมูลชุดนี้สร้าง/แก้ล่าสุดเมื่อไหร่" (dataset แบบ static ไม่ใช่
  วันที่ภาพ)
- **ขนาดจริง**: หนึ่งอำเภอ (พระนครศรีอยุธยา, `ap_idn=1401`) เพียงอำเภอเดียว
  ตอบกลับ **12,829 พิกเซล** — ทั้งประเทศ (~77 จังหวัด x หลายอำเภอ) จึงเป็น
  หลักล้านพิกเซล **ดึงทั้งประเทศในคำขอเดียวจึง timeout จริง** (ตามรายงาน VPS)
  แต่การขอแบบจำกัดจังหวัดเดียว (`pv_idn`) ตอบเร็วมาก (< 1 วินาทีสำหรับหนึ่ง
  อำเภอ, `limit=50`) — ปัญหาคือ **ขอบเขต** (ทั้งประเทศทีเดียว) ไม่ใช่ตัว API
  ช้า → ที่มาของ `tools/build_flood_freq.py` (ดึงทีละจังหวัด, page ใหญ่ 5000,
  บันทึกทันทีทีละจังหวัดเพื่อทำต่อได้ถ้าหลุดกลางทาง)

## 7. `water_hyacinth` — schema คล้าย flood/*day แต่ไม่มี `file_name`

ตัวอย่างจริง (`pv_idn=10`): field ตรงกับ flood/*day (`pv_tn`/`ap_tn`/`tb_tn`
ฯลฯ) แต่ **ไม่มี `file_name`** เลย มีแค่ `_createdAt`/`_updatedAt` และค่านั้น
เก่ากว่าข้อมูลน้ำท่วมมาก (ตัวอย่างที่เจอ: ~2025-10-06 เทียบกับข้อมูลน้ำท่วมที่
อัปเดตวันเดียวกับที่ตรวจ) — **อัปเดตไม่บ่อย** ไม่ใช่ near-realtime แบบชั้น
น้ำท่วม

## 8. `drought-recurrence` (`gi-service/v1.1`) — คนละ family จริงๆ

- **ต้องมี header `Referer`** ตรงกับหน้า dataset ไม่งั้น GISTDA ตอบ
  `403 {"code":"REFERER_REQUIRED"}` — ใส่ header นี้แล้วผ่านทันที (ไม่ใช่
  ความลับ เป็น URL สาธารณะเฉยๆ) แก้ไว้ใน `probe.py`'s `EndpointSpec.extra_headers` แล้ว
- **ผลลัพธ์เป็น array ธรรมดา ไม่ใช่ GeoJSON FeatureCollection** เช่น:
  ```json
  [{"subdistrict_name": "ลาดกระบัง", "district_name": "ลาดกระบัง",
    "province_name": "กรุงเทพมหานคร", "total": 2,
    "detail": [{"year": "2023", "freq": 1}, {"year": "2022", "freq": 0}, ...]}]
  ```
  ข้อมูลถูกสรุปมาให้แล้วระดับตำบล (ไม่ใช่พิกเซลดิบแบบ flood-freq) —
  **ห้ามส่ง `limit`/`offset`** (endpoint นี้ไม่รู้จักพารามิเตอร์นี้ — จะโดน
  ตีความเป็นตัวกรองที่ไม่ตรง กลายเป็น 0 รายการ แบบเดียวกับข้อ 4) แก้
  `probe.py` แล้วให้ endpoint นี้ไม่ผ่านตัวแบ่งหน้า (`records_key=""`)

## 9. ความสดของข้อมูล (สังเกตจากภาพจริง 2026-09-26)

- `flood/1day` — ภาพเดียว วันเดียวกับที่ตรวจ (`rd2_20260926_0613`)
- `flood/3days` — 2 ภาพ (`rd2_20260926_0613`, `rd2_20260924_1815`)
- `flood/7days` — 7 ภาพ ผสมดาวเทียม RADARSAT (`rd2`) และ Sentinel-1 (`S1C`/`S1D`)
- `flood/30days` — 27 ภาพ ย้อนไปถึง `20260828` ผสม `rd2`/`S1C`/`S1D`/`cg2`/`cm4`
  — เห็นชัดว่าเป็นข้อมูลผสมหลายดาวเทียม ไม่ใช่ดวงเดียวคอยถ่ายซ้ำ
- `flood-freq` — static, `_createdAt` ตัวอย่างที่เจอ = 2025-06-17 (ชุดข้อมูล
  ไม่ได้แก้บ่อย)
- `water_hyacinth` — `_createdAt`/`_updatedAt` ตัวอย่าง ~2025-10-06 (เก่ากว่า
  ข้อมูลน้ำท่วมมาก)

## 10. ปริมาณข้อมูล / งบ byte ต่อวัน

`gistda_flood.py`'s เดิมประเมิน national 6 MB × 2/วัน + local 1.5 MB ×
2/วัน/cell ≈ 15 MB/วัน — **ยังใช้ได้** ตัวเลขจากการตรวจสดวันนี้ไม่ขัดแย้ง
(หนึ่งหน้า 50 แปลงในอยุธยา ~90-95 KB, ตรงลำดับกับ MAX_RESPONSE_BYTES/หน้าที่
ตั้งไว้) `flood-freq`'s เองไม่นับในงบนี้ เพราะไม่ใช่การรีเฟรชประจำ — ดึงครั้ง
เดียวผ่าน `tools/build_flood_freq.py` แล้วเก็บเป็นไฟล์ static

## 11. สรุปสิ่งที่แก้ในโค้ดจากผลตรวจนี้

- `kiosk_broker/probe.py`: กล่อง bbox เดิมของ Bangkok เล็กลง (ไม่ครอบอยุธยา
  อีก), `freshness_fields` ใช้ `file_name` (flood/*day) หรือ `_createdAt`
  (flood-freq/water_hyacinth) แทน `img_date`/`date` ที่ไม่มีจริง,
  `drought-recurrence` แก้เป็น `records_key=""` (array ธรรมดา) + header
  `Referer`, เพิ่มสรุปย่อ (≤ 40 บรรทัด) กับ `--out PATH` สำหรับรายละเอียด
  เต็มเป็น markdown
- `kiosk_broker/gistda_flood.py`: `_area_km2` อ่านจาก `flood_area` (ไร่ →
  km²) แทนฟิลด์ที่ไม่มีจริง (`area_km2`/`shape_area_km2`), หักซ้ำ
  `flood_area` ต่อ `tb_idn` (นับครั้งเดียวต่อตำบล ไม่ใช่ต่อแปลง),
  `_district_name` (`ap_tn`) ยืนยันแล้วไม่ใช่การเดาอีกต่อไป, `_feature_date`
  อ่านวันที่จาก `file_name`
- ใหม่: `gistda_flood.flood_freq_km2()`/`load_flood_freq_districts()` —
  อ่านไฟล์ `kiosk_broker/data/gistda_flood_freq_districts.json` (ยังไม่มี
  จนกว่า Poom จะรัน `tools/build_flood_freq.py` บน VPS ด้วย key จริง) คืน
  `None` เสมอถ้ายังไม่มีไฟล์ — ใช้ได้เฉพาะ SHADOW math (`flood_forecast.py`)
  จนกว่า Poom จะยืนยันเงื่อนไขการใช้ข้อมูลของ GISTDA
